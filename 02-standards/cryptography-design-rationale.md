# وثيقة القرارات والتبرير — طبقة التشفير والأمان

> **الغرض:** هذه هي الوثيقة التفصيلية المرافقة للمعيار **SEC-CRYPTO-001**. تشرح **لماذا** اتُّخذ كل قرار (الواقع + المعايير + أفضل الممارسات + موازنة الأمان↔الأداء↔السرعة)، لتكون المرجع الحاكم لأي نقاش مستقبلي. المعيار يحدّد «ماذا»، وهذه الوثيقة تحدّد «لماذا».

## 1. المبدأ الحاكم
نحن **تطبيق ذكاء اصطناعي** (لا تطبيق مالي) مرتبط بتفاصيل دفع. المنهج ليس إعادة اختراع العجلة، بل **دراسة كيف تدير كبرى شركات الذكاء الاصطناعي (OpenAI، Google، Anthropic) التشفير و PII والمصادقة وحوكمة الوصول، ثم تقليدها وتكييفها على واقعنا** مع الحفاظ على الأداء والسرعة.

## 2. القيود الواقعية (Reality Baseline)
### 2.1 البنية التحتية
- **VPS أحادي المستأجر ذاتي الإدارة** لدى مزوّد يمني (Sohobcom «سحبكم»): 16 × XEON core، 64GB RAM، 480GB NVMe، Ubuntu.
- **GPU** لتشغيل استدلال نموذج Gemma **على نفس الـ VPS** ⇒ الـ CPU متفرّغ نسبياً للـ backend (بما فيه تجزئة كلمات المرور).
- لا Cloud backup/firewall/DRaaS مُشتراة بعد. الوصف «On-Prem» غير دقيق؛ الأدق: **VPS مُدار ذاتياً**. البنية قابلة للترقية مستقبلاً.

### 2.2 واقع الكود الحالي
- الجداول: `users`, `otp_codes`, `auth_sessions`, `policy_versions`, `user_consents`.
- كلمة المرور: `Argon2id (t=3, m=64MiB, p=2)`. الهاتف/البريد: `HMAC-SHA-256`. `phone_hash` فريد. لا `phone_enc` بعد.
- `AesGcmCipher` (AES-256-GCM) و`NullCipher` عبر `CIPHER_PROVIDER`. مفاتيح البيئة: `AES_KEY`, `HMAC_KEY`, `JWT_SECRET`.

## 3. نموذج التهديد والأصول (مختصر)
| الأصل | التهديد الرئيس | الضابط |
| --- | --- | --- |
| كلمات المرور | تسريب قاعدة + كسر بالقوة الغاشمة/GPU | Argon2id (memory-hard) |
| PII (الهاتف/الاسم) | تسريب قاعدة، وصول داخلي غير مصرّح | تشفير على مستوى التطبيق + فصل المفاتيح + سجل تدقيق |
| قناة النقل | اعتراض/MITM | TLS 1.3 (1.2 حد أدنى خارجي) |
| المفاتيح | تسريب مفتاح واحد يفكّ كل شيء | فصل المفاتيح + envelope + rotation |
| الوصول الإداري | إساءة صلاحية داخلية | least privilege + تدقيق كل فكّ تشفير |

## 4. تصغير نطاق PCI عبر FinLink
ربط الدفع يتم عبر **FinLink كطرف خارجي** (نمط شبيه بمزوّدات مثل Stripe): معالجة/تخزين بيانات البطاقات (PAN) تقع لديهم لا لدينا. النتيجة:
- نطاق `PCI DSS 4.0` لدينا **مُصغّر** (نمط SAQ-A حين يكون الدفع مُوجَّهاً/مُستضافاً خارجياً).
- يسقط مبرّر «إلزام MFA لمسار الدفع» لأننا لا نحمل بيانات بطاقات.
- يبقى الالتزام الوحيد تجاه FinLink: **جودة قناة النقل (TLS ≥ 1.2)** عند التكامل مع واجهتهم.

## 5. مرجعية ممارسات كبرى شركات الـ AI (Benchmark)
- **التشفير عند التخزين والنقل:** OpenAI تُصرّح باستخدام `AES-256` للبيانات الساكنة و`TLS 1.2+` للنقل — نمطٌ صناعي نتبنّاه. [OpenAI Enterprise Privacy](https://openai.com/enterprise-privacy/)
- **إدارة المفاتيح (envelope encryption):** بنية `DEK/KEK` القياسية في KMS السحابية. [Google KMS — Envelope Encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption) · [AWS KMS — Key Rotation](https://docs.aws.amazon.com/prescriptive-guidance/latest/aws-kms-best-practices/data-protection-key-rotation.html)
- **التشفير على مستوى التطبيق (ALE):** يقلّل ثقة مزوّد البنية/الوصول الداخلي. [Cossack Labs — Application-Level Encryption](https://www.cossacklabs.com/solutions/application-level-encryption/)
- **الفهرس الأعمى (blind index):** البحث على حقول مشفّرة عبر بصمة حتمية مُفتاحة. [SitePoint](https://www.sitepoint.com/how-to-search-on-securely-encrypted-database-fields/) · [Field-level encryption + blind index](https://amitavroy.com/articles/field-level-encryption-with-searchable-blind-indexes-a-practical-soc2-control-worth-understanding)
- **تجزئة كلمات المرور:** `Argon2id` وفق `RFC 9106` وتوصيات OWASP. [RFC 9106](https://datatracker.ietf.org/doc/rfc9106/) · [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- **المصادقة والمخاطر:** مستويات التأكيد في `NIST SP 800-63B`، والـ adaptive/risk-based MFA. [NIST 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html) · [Adaptive MFA](https://www.paloaltonetworks.com/cyberpedia/what-is-adaptive-mfa)

## 6. مصفوفة القرارات المفصّلة
لكل قرار: **القرار** · **البديل المرفوض** · **لماذا (واقع+معيار)** · **الأداء**.

### 6.1 كلمات المرور — Argon2id (t=3, m=64MiB, p=2)
- **القرار:** `Argon2id`، `t=3`, `m=64 MiB`, `p=2`، معايرة ≈0.5s، + concurrency semaphore.
- **البديل المرفوض:** خفض `p=1` «لحماية موارد Gemma على الـ CPU».
- **لماذا:** استدلال Gemma على **GPU**، فالـ CPU متفرّغ؛ لا مبرّر لخفض التوازي. `RFC 9106` يوصي بخيار memory-constrained قريب (t=3/64MiB)، وOWASP يضع حدوداً دنيا أقل — فاختيارنا فوق الحد الأدنى وآمن. الـ semaphore يحمي الـ RAM (كل عملية ≈64MiB) لا الـ CPU.
- **الأداء:** زمن ≈0.5s مقبول لعملية دخول/تسجيل نادرة نسبياً؛ الـ semaphore يمنع انفجار الذاكرة تحت ذروة الدخول المتزامن.

### 6.2 الفهرس الأعمى — HMAC-SHA-256 + pepper
- **القرار:** بصمة حتمية `HMAC-SHA-256` بمفتاح سرّي + `pepper`.
- **البديل المرفوض:** فهرس مشتق من `Argon2/PBKDF2` لإبطاء التعداد على الحقول منخفضة الإنتروبيا (كالهاتف).
- **لماذا:** الفهرس الأعمى يُستدعى في كل بحث/تسجيل دخول؛ فهرس بطيء (Argon2) يقتل الأداء. المفتاح السرّي + الـ pepper يوفّران مقاومة كافية للقاموس ما دام المفتاح غير مسرّب، وهو المعيار الصناعي (CipherSweet default).
- **الأداء:** HMAC شبه فوري (µs)، ومفهرَس (indexable) في القاعدة.

### 6.3 حماية الهاتف — تشفير قابل للعكس + فهرس أعمى (عكس قرار v0.5)
- **القرار:** `phone_enc` = `AES-256-GCM` (قابل للاسترجاع) + `phone_bidx` = `HMAC-SHA-256 + pepper` (بحث/فرادة) + **سجل تدقيق فكّ التشفير**.
- **البديل المرفوض:** الاحتفاظ بـ hash-only (v0.5) دون نصٍّ مشفّر.
- **لماذا:** واجهة الإدارة/الدعم تحتاج **استرجاع** الرقم الفعلي؛ البصمة وحدها لا تسمح بذلك. الفصل بين `phone_enc` و`phone_bidx` يوازن السرّية مع القابلية للبحث. `PDPL/ISO 27701` (Privacy by Design) يبرّران التشفير + تقييد الوصول + التدقيق.
- **الأداء:** فكّ التشفير عند العرض فقط (نادر ومُدقَّق)؛ البحث يتم عبر `phone_bidx` السريع.

### 6.4 التشفير عند التخزين — AES-256-GCM + envelope
- **القرار:** `AES-256-GCM` على مستوى الحقل عبر `CryptoService`، مع `DEK/KEK` وversioning كهدف، وLUKS للوحدة.
- **لماذا:** `AES-256-GCM` هو معيار AEAD الصناعي (OpenAI/Google). التغليف يحدّ من أثر تسريب مفتاح واحد ويتيح الدوران دون إعادة تشفير شاملة.
- **الأداء:** AES-GCM مُسرَّع عتادياً (AES-NI) على XEON — أثرٌ ضئيل.

### 6.5 التشفير أثناء النقل — TLS 1.3 (1.2 خارجي)
- **القرار:** `TLS 1.3` داخلياً؛ `TLS 1.2` حدٌّ أدنى للتوافق مع بوابات خارجية (FinLink) فقط؛ منع 1.0/1.1.
- **لماذا:** `NIST SP 800-52r2` و`PCI DSS 4.0` (حد أدنى 1.2). 1.3 أسرع (مصافحة أقل، 0-RTT) وأكثر أماناً.
- **الأداء:** 1.3 يقلّل زمن التأسيس؛ لا مقايضة سلبية.

### 6.6 المصادقة — OTP لمرة واحدة + MFA اختياري (AAL)
- **القرار:** OTP **لمرة واحدة** لتوثيق ملكية الهاتف عند التسجيل/الربط؛ MFA **اختياري** داخل التطبيق (policy-driven قابل للتوسّع)؛ توثيق المستوى الأساسي بصدق كـ **AAL1**.
- **البديل المرفوض:** فرض 2FA (OTP) على كل عملية دخول، أو إلزام MFA الآن.
- **لماذا:** لا نحمل بيانات بطاقات (الدفع عبر FinLink)، فلا يفرض `PCI DSS` علينا MFA لمسار الدفع. تجربة المستخدم تتحسّن بترك MFA اختياريّاً، مع تصميم قابل للفرض لاحقاً على أدوار حسّاسة (admin) إن استدعت المخاطر — انسجاماً مع منطق الـ adaptive/risk-based MFA دون فرضه إلزامياً الآن.
- **الأداء/التجربة:** دخولٌ أسرع للمستخدم العادي؛ مرونة مستقبلية دون إعادة هندسة.

### 6.7 حوكمة الوصول الإداري
- **القرار:** least privilege، دور `admin` منفصل بصلاحيات منفصلة، **تدقيق كل وصول لبيانات PII (فكّ تشفير)**، وإمكانية فرض MFA على الأدمن عبر مفتاح سياسة مستقبلاً.
- **لماذا:** التشفير على مستوى التطبيق + التدقيق يقلّلان خطر الوصول الداخلي غير المصرّح (ISO 27001 A.8، PDPL).

## 7. الترقيات المستقبلية (Roadmap)
- KMS مُدار (Vault) + envelope كامل + دوران آلي.
- adaptive/risk-based MFA (جهاز موثوق، جغرافيا، سلوك).
- نسخ احتياطي مشفّر خارج الموقع + خطة تعافٍ (DRaaS) عند ترقية البنية.
- تشفير محتوى الرسائل/الذاكرة (messages/memories) في الإنتاج.
