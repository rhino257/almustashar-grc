# معيار التشفير

## 1. الغرض والنطاق
يحدّد هذا المعيار الخوارزميات وأطوال المفاتيح وأنماط التشغيل المسموحة
والمحظورة لحماية البيانات أثناء النقل وعند التخزين، وإدارة المفاتيح، في
تطبيق المستشار القانوني الذكي.

## 2. التشفير أثناء النقل (Data in Transit)
- TLS 1.3 (مفضّل)؛ TLS 1.2 حدٌّ أدنى. ما دونه محظور.
- HSTS مفعّل؛ إعادة توجيه HTTP إلى HTTPS.
```text
TLS 1.3 (preferred):
  TLS_AES_256_GCM_SHA384
  TLS_CHACHA20_POLY1305_SHA256
  TLS_AES_128_GCM_SHA256
TLS 1.2 (minimum):
  ECDHE-ECDSA-AES256-GCM-SHA384
  ECDHE-RSA-AES256-GCM-SHA384
Disabled: TLS 1.0/1.1, SSLv3, RC4, 3DES, static-RSA, CBC-only suites
```
> ملاحظة حوكمة: تشفير النقل **لا يُؤجّل**؛ تكلفته شبه معدومة وهو خط الدفاع
> الأول، خلافاً لتأجيل تشفير التخزين على مستوى الحقل (القسم 9).

## 3. التشفير عند التخزين (Data at Rest)
- الخوارزمية المعتمَدة: **AES-256-GCM** (authenticated encryption).
- التشفير على مستوى الحقل للبيانات الحسّاسة عبر `CryptoService` (القسم 7).
- تشفير القرص/الوحدة (volume encryption) للخادم موصى به كطبقةٍ إضافية.

## 4. التجزئة (Hashing)
| الغرض | الخوارزمية المعتمَدة |
| --- | --- |
| سلامة البيانات / البصمات (عام) | SHA-256 أو SHA-384 |
| التواقيع وسلاسل الشهادات وTLS | **SHA-384 أو أعلى** (الإطار التقني §9) |
| الأسرار قصيرة العمر (OTP) | **Argon2id** + TTL قصير + تحديد معدّل |
| كلمات المرور | **Argon2id** (مُفعّل — أو bcrypt كحدّ أدنى) |
| رمز التجديد (refresh) | **SHA-256** (مخزّنٌ مجزّأً، قابلٌ للإبطال) |
| الفهرس الأعمى / البصمة الحتمية | **HMAC-SHA-256** (هاتف/بريد/بريد الاسترداد) |

> تصحيح: لا يُستخدم SHA المجرّد لتخزين OTP؛ يُكسر بالقوة الغاشمة لقصره.
> كلمات المرور مجزّأة بـ Argon2id فعليّاً (غير مؤجّلة)، شأنها شأن TLS.

### 4.1 نطاق أطوال التجزئة (توضيح ومطابقة مع الواقع)
يشترط الإطار التقني (§9) «SHA-384 أو أعلى». يُوضَّح نطاق هذا الاشتراط تفادياً للّبس، ومطابقةً للكود القائم:
- **التواقيع الرقمية وسلاسل الشهادات وTLS:** تُستخدم **SHA-384 أو أعلى** (كما في مجموعات TLS بالقسم 2). هذا هو نطاق اشتراط الإطار.
- **تجزئة رموز الجلسة (refresh):** يُسمح صراحةً بـ **SHA-256** — الرمز عشوائٌّ عالي الإنتروبيا وقصير العمر، وSHA-256 ملائمٌ تشفيرياً لسلامته (لا يُكسر بالقوة الغاشمة لعشوائية الرمز).
- **الفهرس الأعمى/البصمة الحتمية (هاتف/بريد):** يُسمح صراحةً بـ **HMAC-SHA-256** — دالة مُفتاحة (keyed) تقاوم هجمات القاموس بالمفتاح السرّي؛ ترقيتها إلى HMAC-SHA-384 لا تضيف أماناً عملياً وتكسر التوافق مع الكود القائم.
- **كلمات المرور وOTP:** Argon2id (دالة مُصمّمة للأسرار منخفضة الإنتروبيا) — لا تُقاس بأطوال SHA.

> ⚠️ **انحرافٌ موثّق يحتاج توقيع الراعي:** هذا التخصيص يسمح بـ SHA-256/HMAC-SHA-256 في مواضع التجزئة المُفتاحة/عالية الإنتروبيا خلافاً لإطلاق «SHA-384+» في الإطار التقني §9. مطلوب توقيع راعي المشروع (بصفته CISO/DPO مؤقّتاً) لاعتماده رسمياً — القرار #5 (§11).

## 5. التشفير غير المتماثل والتواقيع
| الغرض | المعتمَد |
| --- | --- |
| RSA | مفتاح >= 3072 بت |
| ECDSA/ECDH | منحنى P-256 أو P-384 |
| التواقيع الحديثة | Ed25519 |

## 6. توليد العشوائية
- مولّد عشوائيٍ آمنٌ تشفيرياً (CSPRNG) حصراً لكل المفاتيح والـ nonces
  وقيم OTP. يُمنع استخدام مولّدات عامة (مثل `random`).

## 7. تطبيق CryptoService (التصميم القابل للتشفير)
- واجهةٌ مجرّدة `Cipher { encrypt(), decrypt() }` مُطبّقة فعلياً بتطبيقين:
  - `NullCipher` (تمرير بلا تشفير) — الافتراضي في التطوير؛ تأجيلٌ مُسجّل (القسم 9).
  - `AesGcmCipher` (AES-256-GCM) — للإنتاج؛ دون أي ترحيلٍ للمخطّط (الأعمدة `TEXT` مهيّأةٌ لحجم النص المشفّر).
- يُختار المزوّد عبر `CIPHER_PROVIDER`.
```text
provider switch via env: CIPHER_PROVIDER = null | aes_gcm
AES key via env/KMS:     AES_KEY  = base64(32 bytes)   # required for aes_gcm
HMAC key (blind index):  HMAC_KEY = base64(secret)     # deterministic *_hash fingerprints
```

الهاتف (الهوية): **لا يوجد `phone_enc`.** يُخزَّن **بصمةً حتمية `HMAC-SHA-256` فقط**
(`phone_hash`) للبحث والفرادة، ولا يُعاد في واجهات القراءة (ARC-API-001 §3). قرارٌ محسوم: هويةٌ بالبصمة دون نصٍّ مشفّر.

الحقول المشفّرة على مستوى الحقل (AES-256-GCM عبر CryptoService) مع بصمة
حتمية `HMAC-SHA-256` (`*_hash`) للحقول القابلة للبحث/الفرادة:
| الحقل | الغرض | بصمة HMAC؟ | الحالة |
| --- | --- | --- | --- |
| `users.email_enc` | عرض البريد الاختياري | نعم (`email_hash`) | 🟢 مطبّق |
| `users.recovery_email_enc` | عرض بريد الاسترداد | نعم (`recovery_email_hash`) | 🟡 مستهدف |
| `messages.content` | محتوى الرسائل (سؤال/إجابة) | لا | 🟡 مستهدف |
| `memories.content` | محتوى الذاكرة الشخصية | لا | 🟡 مستهدف |

- **تخزين كائنات MinIO** (المرفقات، صور الملفّ): تشفيرٌ عند التخزين على مستوى
  الدلو/الوحدة (bucket/volume at-rest)؛ والوصول عبر روابط موقّعة قصيرة العمر فقط (🟡 مع المراحل اللاحقة).
- **البصمة/الـ PIN:** وسيلة قفلٍ محلية على الجهاز، **خارج نطاق هذا المعيار**
  (لا تُخزَّن خادمياً ولا تمرّ بالقاعدة) — ARC-API-001 §3.

## 8. إدارة المفاتيح (Key Management)
- توليد المفاتيح بـ CSPRNG وبالأطوال أعلاه.
- التخزين: مدير أسرار/KMS؛ في الـ MVP تُحقن عبر بيئةٍ محميةٍ خارج Git (`AES_KEY`، `HMAC_KEY`، `JWT_SECRET`).
- الفصل: مفاتيح مختلفة لكل بيئة (dev/prod)؛ لا مفاتيح في الكود إطلاقاً.
- الدوران (rotation): دوريٌّ وعند الاشتباه بالتسريب؛ دعم إصدارات المفاتيح
  (key versioning) لفكّ النصوص القديمة.

## 9. الامتثال والاستثناءات الحالية
- **استثناء مُسجّل:** تأجيل تشفير التخزين على مستوى الحقل في الـ MVP
  (`NullCipher`) مع إلزام أن يكون الكود «قابلاً للتشفير» (القسم 7). يُغلق
  الاستثناء عند تفعيل `AesGcmCipher`.
- **غير مشمولٍ بالتأجيل:** تشفير النقل (TLS، القسم 2) وتجزئة كلمات المرور
  بـ Argon2id (القسم 4) والفهرس الأعمى HMAC — كلها إلزاميةٌ فوراً.

## 10. المحظورات
محظورٌ صراحةً: MD5، SHA-1، DES/3DES، RC4، نمط ECB، مفاتيح مضمّنة في
الكود (hardcoded)، وتطوير خوارزميات تشفيرٍ ذاتية (roll-your-own crypto).

## 11. القرارات المفتوحة

| 2 | KMS مُدار مقابل حقن البيئة | يُحسم عند الإنتاج |

| 5 | نطاق SHA-384+ مقابل السماح بـ SHA-256/HMAC-SHA-256 | **محسوم: تخصيص موثّق (§4.1) — بانتظار توقيع الراعي (CISO)** |
| 6 | هوية الهاتف بالبصمة مقابل تشفيره | **محسوم: hash-only (لا phone_enc)** |
