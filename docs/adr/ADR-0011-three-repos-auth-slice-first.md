# ADR-0011: ثلاثة مستودعات منفصلة، والبدء بشريحة المصادقة

## الحالة
Accepted — 2026-07-16

## السياق

«المستشار القانوني الذكي» مساعد قانوني يمني يجب أن يعمل **محلياً بالكامل داخل اليمن (On-Prem)**، مع متطلّبات صارمة لسيادة البيانات والخصوصية والعزل الأمني.

يتكوّن النظام من ثلاثة اهتمامات ذات دورات حياة ومهارات وأهداف نشر وحدود أمنية مختلفة جوهرياً:

1. **تطبيق Flutter للهاتف** — واجهة المستخدم، يُوزَّع على المتاجر/الأجهزة.
2. **خادم FastAPI** — API + PostgreSQL (pgvector) + الاستدلال؛ يحوي كل البيانات الشخصية والقانونية؛ يعمل On-Prem.
3. **الحوكمة والامتثال (GRC)** — مواصفات الحوكمة، ضوابط ISO/IEC 27001، إرشادات OWASP LLM، والوثائق القانونية/السياساتية.

قوى إضافية:
- يتبع الخادم تصميم **العقد أولاً، سداسي (hexagonal)، أحادي معياري**، ويجب أن يكون **المالك الوحيد لعقد الـ API**.
- نريد التسليم **تدريجياً** وإثبات المعمارية طرفاً لطرف قبل توسيع النطاق.
- يعمل المطوّرون البشر ووكلاء الذكاء الاصطناعي أسرع مع **مستودعات صغيرة ومركّزة** تناسب نافذة سياق نظيفة.

## محرّكات القرار
- فصل واضح للاهتمامات والملكية.
- CI/CD وإصدارات مستقلة لكل مستودع.
- حدّ أمني صارم يعزل الخادم والبيانات On-Prem عن العميل.
- تكامل قائم على العقد عبر `openapi.json` وحيد ومملوك.
- مستودعات أصغر أسهل على البشر ووكلاء الذكاء الاصطناعي.

## الخيارات المدروسة
1. **مستودع أحادي (Monorepo) للثلاثة معاً** — *مرفوض.* يطمس الحدّ الأمني المطلوب للعزل On-Prem، ويربط النشر وإيقاع الإصدار، ويصعّب ملاءمة نافذة سياق الوكيل.
2. **مستودع مدمج للتطبيق + الخادم (والحوكمة منفصلة)** — *مرفوض.* يظل يربط دورتَي حياة العميل والخادم ويضعف حدود المنتِج/المستهلك في نهج العقد أولاً.
3. **ثلاثة مستودعات منفصلة** ✅

## القرار

نعتمد **ثلاثة مستودعات Git منفصلة**:

| المستودع | المسؤولية | مجموعة `docs/` الخاصة |
|---|---|---|
| `almustashar` | تطبيق Flutter (العميل) | وثائق الواجهة |
| `almustashar-api` | الخادم — FastAPI، PostgreSQL + pgvector، محوّلات الاستدلال. **يملك عقد الـ API (`openapi.json`)**. المجلد المحلي: `almustashar_backend`. | مجموعة وثائق الخادم الكاملة |
| `almustashar-grc` | الحوكمة والمخاطر والامتثال والوثائق القانونية/السياساتية | وثائق الحوكمة |

المبادئ:
- **كل مستودع مكتفٍ ذاتياً** بمجموعة وثائقه.
- **يُزامَن الفهم المشترك عبر عقد الـ API (`openapi.json`)** و«سجل الحقيقة الواحدة (SSOT)» في Notion — **لا** بتكرار الكود أو وثائق التصميم بين المستودعات.
- **يبدأ التسليم بشريحة المصادقة (المرحلة أ)**، منفَّذة **عمودياً عبر كل طبقات الخادم أولاً** قبل أي ميزة أخرى — للتحقق من المعمارية السداسية، وRLS المغلق افتراضياً، والنموذج الأمني، وعقد الخادم↔الواجهة طرفاً لطرف.

## النتائج (Consequences)

### إيجابية
- فصل واضح للاهتمامات والملكية.
- CI/CD وإصدارات مستقلة لكل مستودع.
- حدّ أمني صارم: يبقى الخادم والبيانات On-Prem معزولين عن العميل.
- تكامل قائم على العقد عبر `openapi.json` وحيد ومملوك.
- شريحة المصادقة العمودية تقلّل مخاطر المعمارية مبكراً.

### سلبية / مقايضات
- يجب إبقاء عقد الـ API **متزامناً** بين الخادم (المنتِج) والواجهة (المستهلك).
- التغييرات العابرة للمستودعات تتطلّب **تنسيقاً**.
- كل مستودع يصون بنية `docs/` موازية.
- لا يوجد سحب واحد «يبني كل شيء دفعة واحدة».

### متابعات / تخفيفات
- **تجميد وإصدار `openapi.json`** كعقد رسمي، وحذف أي عقد قديم مكسور.
- إبقاء وثائق كل مستودع و«SSOT» في Notion **متسقة**.
- إرساء **CI في كل مستودع**.
